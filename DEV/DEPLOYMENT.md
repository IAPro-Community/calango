# Deployment — Calango on your VPS

Status: design. The Dockerfiles were built on 2026-11-22 and the health checks passed with `--network host` (see `VERIFY.md`). Port mapping through bridge networking remains unvalidated. In this session the sandbox blocked access to the Docker daemon, so the images were not revalidated.

## Model

```
Person's VPS                           clients
┌──────────────────────────┐          ┌─────────────┐
│ docker: calango          │◄──TLS────│ desktop     │
│  - core, routines        │          │ iOS         │
│  - browser (chromium)    │          │ Android     │
│  - data (SQLite in vol)  │          │ web         │
└──────────────────────────┘          └─────────────┘
```

The server is the only place where the agent runs, stores data and executes routines. Clients are remote controls: they do not run the agent; they only show state and send commands. That is why the agent stays alive when the laptop is off, and the phone works from anywhere.

It also works with the server on the computer itself (local mode). Same binary; only the address changes.

## Pairing

1. The person starts the container on the VPS.
2. The server shows a single-use pairing code (QR or text), valid for a few minutes.
3. The app reads the code, exchanges it for a device token and stores the token in the system keychain.
4. Each device can be revoked separately.

## Secure access (required)

- **Never expose the port in plain text.** Everything goes through TLS, via a reverse proxy (Caddy or Traefik with automatic certificates) or over a private network.
- **Behind a reverse proxy**, set `CALANGO_TRUSTED_PROXIES` to the proxy's address. Without it, every client behind the proxy shares one pairing rate-limit bucket.
- **Alternative without a public port**: a private network (Tailscale or WireGuard). Recommended as the default for anyone who does not want to expose the VPS.
- Strong administrator password on first access; no default credentials. Not implemented yet: see "Administrator password" below.
- Device tokens with scope and expiry; immediate revocation.
- Secrets (model keys, connector tokens) encrypted at rest, with the key kept outside the data volume.

## One-line VPS install

`deploy/install.sh` (POSIX `sh`) installs the official image behind Caddy on a Linux VPS that already has Docker Engine and the Compose v2 plugin. It does not install Docker and runs no third-party script.

```sh
curl -fsSL https://raw.githubusercontent.com/IAPro-Community/calango/vX.Y.Z/deploy/install.sh -o install.sh
less install.sh
sudo sh install.sh --domain calango.example.com --version vX.Y.Z
```

Piping also works (`curl -fsSL …/install.sh | sudo sh -s -- --domain … --version …`); the whole script runs inside `main`, so a truncated download executes nothing. Fetch the script from the same tag as the image.

What it does, in order:

1. Checks root, `docker`, the daemon and `docker compose`.
2. Creates `/opt/calango` (`--dir`), mode `0750`.
3. Creates the vault key once: `secrets/vault.key`, base64 of 32 random bytes, owner UID/GID 65532 (the image's `nonroot`), mode `0400`, in a `0700` directory. The key is never printed or logged. If the key is missing but the data volume exists, the installer stops instead of creating a new key that cannot open the stored secrets.
4. Pulls the image and pins it by digest (`CALANGO_IMAGE=ghcr.io/iapro-community/calango@sha256:…` in `.env`; the human tag is kept in `CALANGO_SOURCE_IMAGE`).
5. Writes `.env`, `docker-compose.yml` and `Caddyfile` (generated by the script; `deploy/docker-compose.yml` and `deploy/Caddyfile` are byte-identical copies and CI fails on drift).
6. Runs `docker compose up -d`, waits for `calango healthcheck`, then checks `https://<domain>/healthz` through Caddy with `curl --resolve` (a warning, not an error, while DNS or the certificate is pending).
7. Prints how to read the local token without logging it: `sudo docker compose -f /opt/calango/docker-compose.yml exec calango calango print-token`.

Re-running is idempotent: the key, the volumes and therefore the token stay; configuration and image are rewritten. `--version` upgrades. `--uninstall` removes the containers and network and keeps volumes, key and configuration; `--uninstall --purge` also deletes volumes, key and the directory, after typing `APAGAR` or with `--yes`. `--tls-internal` uses Caddy's internal CA for tests and LANs; `--image` and `--no-pull` use a local or mirrored image; `--subnet` changes the Compose subnet if `172.30.117.0/24` is taken.

Compose layout:

- `data-init` (`busybox:1.37`, no network) runs `chown 65532:65532 /data` on the named volume and exits. This covers images built before the Dockerfile itself prepared `/data` (PR #154) and is a no-op afterwards.
- `calango`: no published port, only `expose: 7317` on the Compose network. `CALANGO_DATA_DIR=/data`, `CALANGO_VAULT_KEY_FILE=/run/secrets/calango_vault_key` (a Compose file secret; outside Swarm it is a bind mount, so the host file's owner and mode apply), `CALANGO_TRUSTED_PROXIES` set to the Compose subnet (only Caddy and the node are on it). `cap_drop: ALL`, `no-new-privileges`. The health check runs `calango healthcheck`, a subcommand that queries the daemon's loopback `/healthz` because the distroless image has no shell or curl.
- `proxy` (`caddy:2.10`): ports 80, 443 and 443/udp; starts after the node is healthy; automatic HTTPS for `CALANGO_DOMAIN` (`CALANGO_TLS=acme`) or `tls internal` (`CALANGO_TLS=internal`). Health check on Caddy's admin endpoint inside the container.

Manual use without the installer: put `.env` (`CALANGO_IMAGE`, `CALANGO_DOMAIN`, optionally `CALANGO_SUBNET`, `CALANGO_TLS`) and `secrets/vault.key` (owner 65532, mode 0400) next to `deploy/docker-compose.yml` and `deploy/Caddyfile`, then `docker compose up -d`.

Back up `secrets/vault.key` encrypted and off the VPS, separately from the data volume; see [BACKUP_RESTORE.md](BACKUP_RESTORE.md). Docker volume backup/restore is still unvalidated.

### Image publication

`.github/workflows/release-image.yml` publishes `ghcr.io/iapro-community/calango:X.Y.Z` for `linux/amd64` and `linux/arm64`, only from a `vX.Y.Z` tag push or a `workflow_dispatch` naming an existing tag. Each architecture builds natively (`ubuntu-latest` and `ubuntu-24.04-arm`) and is pushed by digest with BuildKit provenance (`mode=max`) and SBOM; a final job creates the multi-arch index with OCI annotations (title, AGPL-3.0-only, source, revision, version), refuses to overwrite an existing version, and adds a signed GitHub build-provenance attestation (`gh attestation verify oci://ghcr.io/iapro-community/calango@sha256:… --repo IAPro-Community/calango`). There is no `latest` tag. It uses only `GITHUB_TOKEN` with `packages: write`. The package's visibility must be set to public by a maintainer after the first publication.

Pull requests do not publish: `ci.yml` builds the image on amd64 (`node-image`) and natively on arm64 (`node-image-arm64`, with a `/healthz` run), and `vps-installer` runs shellcheck, the drift check, and a clean install, reinstall, uninstall and purge on the runner.

### Administrator password

`DEV/SPECS/modules/pairing-auth.md` requires an administrator password on the first start of the VPS node, but does not define the flow: how the password is set without a default credential, where its hash lives (it needs a migration), what it unlocks compared with the local token and device pairing, and recovery. It is therefore not implemented, and the installer does not invent one. Until it is specified, administration on the VPS requires root shell access: the local token (`print-token`) and pairing codes are obtained only from inside the server, never over the network or in logs.

## Push notifications (mobile)

A self-hosted server cannot talk directly to APNs (iOS) or FCM (Android) without Apple and Google credentials. Proposal: a small **push relay**, hosted by us, which receives a notice from the person's server and forwards it to their phone. The relay sees no content: it only sends "there is news", and the app fetches the content from the person's server. This is also a monetization point (see [MONETIZATION.md](MONETIZATION.md)).

## Updates

- Versioned image (`ghcr.io/iapro-community/calango:<version>`, pinned by digest by the installer). Updating means re-running the installer with `--version` (or changing the tag and restarting).
- Database migrations run at startup and have no down-migrations. Take an offline snapshot before upgrading.
- The local-node backup procedure, vault-key requirements and restore-before-rollback policy are in [BACKUP_RESTORE.md](BACKUP_RESTORE.md). Docker volume backup/restore remains unvalidated.

## Managed hosting (paid option)

For those who do not want to run a VPS, offer the same server hosted by us, with the same APIs. This corresponds to the Pro/Team plan in [MONETIZATION.md](MONETIZATION.md). The self-hosted version remains available, so the product does not depend on us to exist.
