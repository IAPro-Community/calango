# ADR 0019 — Desktop shell and local token handoff

Status: accepted · 2026-11-23 · implements the desktop beta (F1-T20 to F1-T23) · builds on ADR 0012 (vault envelope) and ADR 0009 (Maestro isolation is unchanged).

## Context

The owner wants the beta running on his screen. The desktop spec (`DEV/SPECS/modules/desktop-electron.md`) fixes an Electron shell that starts `calango`, waits for `/healthz`, restarts it with backoff, and gives the renderer only the `sdk-ts` client.

The renderer needs the local API token to call `/v1`. The token is generated by the daemon and kept in the vault (`api-token`, ADR 0012). The vault is encrypted in SQLite, and no route returns a secret value. The desktop therefore needs a way to read the token that does not add a route that returns it, does not write a file that holds it, and does not put it in a log.

## Decision

1. **Token handoff through `calango print-token`.** The binary accepts the subcommand `print-token`. It opens the store, loads the master keys without rotating them, loads or creates the `api-token` in the vault, writes the token to stdout with no trailing newline, and exits. Errors go to stderr. The daemon itself is unchanged in what it serves.
2. **The Electron main process holds the token in memory.** It runs `calango print-token` once per daemon start, keeps the value in a variable, and passes it to the renderer only through the preload (`contextBridge`, one method that returns the token and the base URL). The token is never written to disk, never logged, and never stored in `localStorage`.
3. **Rejected alternatives.**
   - A route that returns the token: it widens the API surface and a leaked device token could read the owner's token.
   - A token file in the data dir: a second copy of a secret outside the vault.
   - A token in an environment variable set by Electron: it would be visible to child processes and in process listings.
4. **Supervisor.** The main process spawns the binary with the same environment, waits for `GET /healthz` with a 200, and restarts the daemon with backoff (250 ms, doubling, capped at 4 s) when it exits. A restart fetches the token again. The renderer shows the daemon state from the main process.
5. **Renderer boundary.** The renderer uses only `packages/sdk-ts`. It runs with `contextIsolation: true`, `sandbox: true`, no `remote`, and a strict CSP (`connect-src` limited to the daemon address).
6. **Refresh by polling for the beta.** Messages, runs, approvals and routines are polled while a screen is open. `/v1/events` (WebSocket) needs a token in a header that browsers cannot set; it is deferred until a design for that is approved.
7. **Scope.** Tests and the first run are on Linux only (owner decision). Windows and macOS packaging, keyring backends and notarisation stay out of the beta.

## Consequences

- `print-token` runs the vault unlock path, so a locked or missing keyring fails the desktop start with a visible error, not a silent empty token.
- A daemon restart requires a second `print-token`; the renderer receives the new token after the main process restarts the daemon.
- Anyone who can run `calango print-token` on the machine can read the token. This is the same trust as reading the vault on that machine, and the token already controls the local node.
- Polling costs one request per open screen every few seconds. Acceptable for a single-user local node; revisit with WebSocket when a header-capable design is approved.

## Implementation addendum (2026-11-23)

- The desktop renderer origin is exactly `app://calango`; the API allows only that CORS origin, with no wildcard (`cmd/calango` and `internal/api/cors_test.go`).
- Electron removes `node_modules/.bin` entries from the daemon child's `PATH`. npm/npx may prepend them and shadow the user's authenticated `codex`; all other PATH entries are preserved.
